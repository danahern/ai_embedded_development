    1. Introduction
The Alif DevKit is a development device containing an Alif Ensemble multi-core high-performance, low-
power consumption embedded device. It consists of multiple Cortex-M class and Cortex-A class
processors on a single device. The Cortex-A32 processor present in the device is a low-power 32-bit
ARMv8-A only processor that offers ultra-high efficiency in computing. The Application Processor Sub
System (APSS) is made up of one or more Cortex-A32 cores, which can be used to run high-level/rich
operating systems like Linux.

The APSS in the DevKit Ensemble device has the following features,
    • CPU core(s) operating at 800MHz.
    • CPU core(s) each with L1 instruction cache of 32KB, L1 data cache of 32 KB.
    • Total L2 cache of 512KB.
    • SRAM (static random-access memory) of 4MB.
    • MRAM (Magnetoresistive Random Access Memory) of 6MB
    • Advanced SIMD and floating-point support.
    • GIC-400 (Generic Interrupt Controller) support.
    • Supports execution state at all Exception levels (EL0 to EL3).
    • Performance Monitoring Unit (PMU).
    • Embedded Trace Macrocell (ETM).

In this User Guide, we will focus on downloading the installing the pre-built images necessary to run the
beta version of the Alif Linux distribution on the Ensemble DevKit using OSPI flash and OSPI HyperRAM.

A list of the drivers supported in this pre-built release image is available in section 7.

3.3 Extracting the Release and Copying Pre-Built Images and Configuration Files

Loading Prebuilt Alif Linux Images
Copy the prebuilt images and config files to the appropriate SETOOLS directory.
       $ cd /home/$USER/alif_linux-0.5.2/config-files
       $ cp *.* /home/$USER/app-release-exec-linux/build/config
       $ cd /home/$USER/ alif_linux-0.5.2/prebuilt-images
       $ cp *.* /home/$USER/app-release-exec-linux/build/images

There are two sets of pre-built images available.

MRAM Operation:
This set of images stores all four Linux images (bl32, device tree, kernel, and file system) in the on-chip
MRAM. On-chip SRAM is used for kernel memory. The advantage of this distribution is that it can be
programmed using a single SETOOLS command. This distribution supports SD-share, USB, I2C, SPI, CRC,
and GDB debug using UART4.

OSPI Flash Operation:
This set of images stores the boot loader (bl32) and device tree in on-chip MRAM but stores the larger
kernel and file system images in the off-chip OSPI flash memory. This uses much less of the on-chip
MRAM so it is available for M55 real-time applications but requires multiple steps to load both the off-
chip OSPI flash and the on-chip MRAM. This distribution supports the peripherals in the MRAM
distribution plus Ethernet.

    6 Debugging An Application with GDB Over Serial Cable

6.1 Overview
Linux userspace embedded applications are usually debugged using GNU Debugger (GDB), a portable
debugger that runs on many Unix-like systems. The same method is used in this user guide to debug
userspace embedded applications running on the APSS.

The GDBserver tool of GDB is a computer program that makes it possible to remotely debug the Linux
userspace applications. The GDBserver runs on the target system (DevKit Ex) as the applications to be
debugged, it allows the client GDB tool to connect from another system (host machine either Windows
10 or Linux in our case); that is, only the application to be debugged needs to be resident on the target
system (Devkit Ex), while the source code and a copy of the binary file (with debug symbols) to be
debugged reside on the developer's local computer ("host"). The connection can be either ethernet or a
serial line.


The following figure shows schematic view of how remote debug using GDB client-server via serial
(UART4 port) works.

 Host – Linux                                                            Target – Devkit device




          GDB                                                                     GDB
         client                 Serial cable (USB - UART 4 port)                 server




    1. GDBserver is launched on the Devkit device, with the arguments:
          a. The serial device name (e.g.: /dev/ttyS2) of the UART4 port.
          b. The path and filename of the executable to be debugged.
               It then waits passively for the host gdb to communicate with it.
    2. GDB is run on either Linux or Windows 10 host, with the arguments:
          a. The path and filename of the executable (and any sources) on the host, and
          b. The USB device name (e.g: /dev/ttyUSBx for Linux Host) of USB port, which is used to
               connect with the Devkit device.

6.2 Prerequisites
To debug userspace embedded applications using a GDB client- server model using serial cable which is
connected to UART4 of the development kit at one end and to a USB port of the Linux host at other end,
it is necessary to use a distribution with serial (UART4) support so that the Devkit device communicates
with the host machine and vice-versa. The embedded Linux application to be debugged is copied into an
ext4 partition of an SD card which is mounted within the Linux rootfs.

The pre-built images that were programmed into the development kit in the previous section have these
features enabled and can be used to do GDB client-server debugging of user applications.

Because the Ensemble DevKit Gen 2 only has the SEUART and one of the UART ports available on the
micro-USB connector, the normal setup for Linux is to have the jumpers set to have UART2 appear on
the micro-USB connection for use as the console.

An external FTDI adapter needs to be hooked up to get simultaneous access to UART4 for debugging at
the same time as UART2 for the Linux console. The instructions for connecting an external FTDI adapter
to UART4 are in section 3 of this document.


In order to determine which ttys port is being used for UART4, it is suggested that you check the dmesg
file with the following command:

        root@devkit-e7:/var/volatile/Symetrica# dmesg |grep tty
        Kernel command line: console=ttyS0,115200n8        root=mtd:physmap-
        flash.0         rootfstype=cramfs        ro      loglevel=9
        printk: console [ttyS0] disabled
        4901a000.uart2: ttyS0 at MMIO 0x4901a000 (irq = 128, base_baud = 6250000) is a 16550A
        printk: console [ttyS0] enabled
        4901c000.uart4: ttyS1 at MMIO 0x4901c000 (irq = 129, base_baud = 6250000) is a 16550A

In this case, it is obvious that UART4 is on ttyS1.

7.1 MHU (Message Handling Unit)
MHU facilitates the communications between two independent cores using Linux Kernel’s Mailbox and
RPMSG driver on a Heterogeneous Multicore Processing (HMP) platform like DevKit.

An MHU has two halves. A Sender frame and a Receiver frame, sometimes referred to as Sender and
Receiver. The MHU facilitates communication between two cores, with one core having the Sender and
the other having the Receiver of a single MHU. MHUs are implemented in pairs to allow for full-duplex
communications, with Sender and Receiver being reversed between the two MHUs in the pair.

On the APSS, the Linux Kernel xipImage can transfer/receive
    • 8 bytes of data at a time (4 bytes on each channel) on MHU 0 (secure)
    • 8 bytes of data at a time (4 bytes on each channel) on MHU 1 (non-secure)
The APSS communicates with the following sub-system via MHU 0 and 1
    • APSS and RTSS-HP sub system.
    • APSS and RTSS-HE sub system.
    • APSS and SE sub system.

7.2 HWSEM (Hardware Semaphore)
A semaphore is a variable or abstract data type that provides a simple but useful abstraction for
controlling access by multiple cores/processes to a common resource in a multi-core environment like
there is in the Ensemble DevKit. The DevKit supports a total of 16 hardware semaphores. Their purpose
User Guide                                                                      Preliminary Information
                                                     23
AUGD0003 v0.5.2_3 – July 2024
                                                          User Guide - Getting Started with Linux

is to control and facilitate access to a shared resources or perform critical operations without conflicts or
race conditions between two or more cores.

The following guidelines should be followed while performing a critical operations or access to a shared
resource.

    •   Each core has to lock the HWSEM, by writing its MASTER_ID into the corresponding HWSEM
        base address before performing the critical operation or access to a shared resource.
    •   The core holding HWSEM should unlock/release the HWSEM after performing the critical
        operations.
    •   Other cores should wait/block on HWSEM if the specific HWSEM is already locked by another
        core.

To facilitate the above, the HWSEM driver in the Linux Kernel allows,

    •   Locking a specific HWSEM by writing MASTER_ID into the corresponding HWSEM base address.
    •   Reading current MASTER_ID of a particular HWSEM from an offset address (to know the core
        which locked HWSEM).
    •   Reading HWSEM count from an offset address (the number of times the particular HWSEM is
        locked).
    •   Unlocking HWSEM, so that other cores can lock it.



The following Linux Kernel configurations are enabled to support HWSEM:
CONFIG_HWSPINLOCK=y
CONFIG_HWSEM_ALIF=y

7.3 Watchdog (SBSA Generic Watchdog timer)
Most embedded systems need to be self-reliant. It’s not usually possible to wait for someone to reboot
them if the software hangs or system crashes. Some embedded designs, such as space probes, are
simply not accessible to human operators. If their software ever hangs, such systems are permanently
disabled. In other cases, the speed with which a human operator might reset the system would be too
slow to meet the uptime requirements of the product.
A watchdog timer is a piece of hardware that can be used to automatically detect software anomalies
and reset the processor if any occur. A watchdog timer is based on a counter that counts down from
some initial value to zero. The embedded software selects the counter’s initial value and periodically
restarts it. If the counter ever reaches zero before the software restarts it or refresh the counter, the
software is presumed to be malfunctioning and the processor’s reset signal is asserted. The processor
(and the embedded software it’s running) will be restarted as if a human operator had cycled the power.
Below figure shows the working of Watchdog module

AUGD0003 v0.5.2_3 – July 2024
                                                       User Guide - Getting Started with Linux




 The Arm SBSA Generic Watchdog has two-stage timeouts: The first signal (WS0) is for alerting the
system by interrupt, The second one (WS1) is a real hardware reset that reboots the system. The
working of the generic watchdog is as:

   •   Generic Watchdog act either as a single stage watchdog or a two stages Watchdog, it's set up by
       the module parameter "action".
   •   In the single-stage mode, when the timeout is reached, the host system will be reset by WS1.
       The first signal (WS0) is ignored.
   •   In the two stages mode, when the timeout is reached, the first signal (WS0) will trigger panic
       basically an interrupt will be generated and serviced by the interrupt handler. If the system is
       getting into trouble and cannot be reset by panic or restart properly by the kdump kernel (if
       supported), then the second stage (as long as the first stage) will be reached, the system will be
       reset by WS1 signal.

7.9 CRC

Overview
Cyclic Redundancy Check (CRC) is a commonly used way to verify the integrity of a message. The CRC
algorithm computes a digest for a given message following a certain computation. The computation
involves dividing the given message (in its binary representation form) by a polynomial repeatedly and
finding the remainder. This remainder is the CRC for the given message. There are many CRC algorithm
types and they differ in the polynomial they choose (the polynomial can be of order 8, 16 or 32). The
result size of the CRC algorithm depends on the polynomial chosen. The result size for CRC32, CRC16
and CRC8 algorithms are 32 bits, 16 bits and 8 bits respectively.

Implementation
The Alif CRC module supports the following 5 different CRC algorithms.
    • CRC-8-CCITT
    • CRC-16
    • CRC16-CCITT
    • CRC-32
    • CRC-32C

The Alif CRC module outputs the CRC for an input data based on the values set in the below control
registers.
    1. Init register - Configures the required algorithm type.
    2. Seed register - Writes the seed value.
    3. Data registers - Writes the input data either 4 bytes at a time (for CRC32) or 1 byte at a time (for
         CRC8 and CRC16).
Once all data has been written, the CRC output/result read from the result register.

The register address information can be found in the CRC hardware reference document.

The Alif CRC module functionality is used for the APSS using Linux kernel device driver. The driver
registers with the Linux crypto subsystem for all the above algorithms.
