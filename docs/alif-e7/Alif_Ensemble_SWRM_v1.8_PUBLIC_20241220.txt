1 Preface
   The Ensemble™ family of fusion processors and microcontrollers from Alif Semiconductor creates a scalable
   and compatible continuum of highly integrated processors for use in intelligent embedded Internet of Things
   (IoT) applications. Architected for power efficiency and long battery life, it delivers high computation and
   Machine Learning / Artificial Intelligence (ML/AI) imaging, audio and sensing capability, wired multi-layered
   security, and highly interactive human-machine interface.
   Individual selections within the Ensemble family of devices scale up, starting with single-core MCUs, to dual-
   core MCUs, triple-core MCU/MPU fusion processors, and quad-core MCU/MPU fusion processors, to meet
   the needs of a broad range of IoT applications. The devices share a common set of peripherals and power
   management schemes and are built on a unified interconnection fabric that simplifies software and hardware
   reuse across diverse projects.
   The following table is a top-level feature view of the device family:

   Inter-Process Communication (IPC), and power management options.
   For detailed specifications, functional descriptions, and device features and peripherals supported, refer to

2 Overview of the Device System Architecture

2.1 System Architecture
   Embedded system designers need to balance many, often contradictory requirements: high-performance vs.
   high-efficiency, security vs. application flexibility, device versatility vs. low latency. Alif Semiconductor's
   system architecture is designed with the goal of creating powerful and highly scalable solutions that
   efficiently address these challenges.
   The system architecture is comprised of multiple subsystems optimized for specific roles. Each subsystem has
   one or two CPUs, an optional Neural Processor Unit (NPU), memory, and peripherals. Each subsystem can
   execute code independently of others, but may share a power domain and can access shared memory and
   peripherals. The subsystems running in a specific power domain are referred in this document as execution
   domains. Each of them can be considered as a microcontroller optimized for a specific class of embedded
   applications.
   The system architecture includes the infrastructure required to integrate and manage the different execution
   domains (see Figure 2-1). The backbone of the system interconnect is based on a high-performance
   interconnect fabric. It is secured by a number of Firewalls that monitor all master and slave ports on the bus.
   The Firewalls can filter transactions based on the desired security policy and perform address translation
   when an execution domain requires a different view of the global address map.

2.3 Application Processor Subsystem (APSS)
   The APSS hosts up to two Arm Cortex-A32 cores outfitted with an ample amount of cache. Each Cortex-A32
   core has a 32KB instruction and a 32KB data Level 1 cache. Both cores share 512KB of Level 2 cache with a
   built-in cache coherency controller. The cache size is chosen to maximize processor performance, given that
   the system memory blocks have different and limited bandwidth. This approach enables balance between
   performance and energy efficiency.
   The APSS is optimized for running Linux-based embedded applications that can benefit from the power
   efficiency and high-performance of the Cortex-A32 cores (see Figure 2-3).

   The APSS includes an interrupt controller that handles interrupt requests from local and shared peripherals.
   The local peripherals include MHU that enables IPC to the SESS and to the other subsystems.
   The Cortex-A32 cores include a full-featured Memory Management Unit (MMU), enabling execution of a
   Linux® operating system. The Linux kernel can be configured with Symmetric Multiprocessing (SMP) support,
   making most of the dual-core performance capabilities.
   Alternatively, the Cortex-A32 cores can be utilized by several SMP-capable Real-Time Operating Systems
   (RTOS), such as Azure RTOS (formerly ThreadX).

2.4 Real-Time Subsystem (RTSS)
   The Ensemble family of devices has two RTSSs (except for E1 devices, which have one), each featuring a
   Cortex-M55 CPU with Tightly Coupled Memory (TCM) and, optionally, one or two Ethos-U55 microNPUs (see
   Figure 2-4). The High-Performance RTSS (RTSS-HP) is optimized for fast compute performance, and the High-
   Efficiency RTSS (RTSS-HE) is optimized for power-sensitive use cases. Both RTSS-HP and RTSS-HE enable
   highly deterministic control or data collection applications. Both RTSS also feature MHUs that facilitate IPC,
   and programmable Direct Memory Access (DMA) controllers that off-load data movement tasks.
   The Cortex-M55 in the RTSS-HP can operate at up to 400 MHz core clock frequency. The single-cycle 256KB
   Instruction Tightly Coupled Memory (ITCM) and 1MB Data Tightly Coupled Memory (DTCM) enable a highly
   deterministic, high-performance execution environment capable of running tight control loops with minimal
   jitter. The RTSS-HP also has its own Ethos-U55 microNPU ML accelerator with capacity of 256 MACs. The
   faster clock frequency, larger TCM capacity, and increased number of MAC(s) in the RTSS-HP provide
   resources for implementation of advanced neural networks and faster, more accurate inference execution.

   The implementation of the Cortex-M55 in the RTSS-HE is optimized for low current consumption while

2.5 Shared Memory
   The Ensemble family of devices integrates large amounts of SRAM distributed across multiple SRAM blocks,
   each with different performance, bandwidth, and power consumption. This is done to enable users with full
   flexibility to partition the memory among the various execution domains based on the needs of their
   application.
   The different types of memory blocks and their characteristics are described in Table 2-1.
                                          Table 2-1 Shared Memory Distribution

                Type                                                                    Description
                                         The bulk of the SRAM is split between two blocks—SRAM0 and SRAM1 . They are
Shared SRAM                              shared with all cores. This enables the concurrent access to the memories from
                                         different execution domains.

                                         SRAM can be used to retain the system state needed to control different system
Backup SRAM                              wakeup scenarios. The backup SRAM is 4KB and can only hold data. The CPU cores

                                         should be 32-bit wide.

2.6.3 Peripherals Security
   In secure state, the access to the peripheral registers is controlled by Firewalls (similarly to the access control
   of the shared memory regions). The Firewalls perform the role of Peripheral Protection Controller described
   in the TrustZone documentation. The peripheral protection is set by the SE in response to application
   requests to assume control over specific peripheral. This is done by preventing unauthorized access—
   excluding the transactions with invalid master ID and a Non-Secure (NS) side signal.
   Peripherals in the Ensemble family of devices are designed to support low-power operation and to minimize
   energy consumption when not in use. Each peripheral instance has a clock gating circuit controlled by
   dedicated register bits. The clock gating control has two register stages—one controlled by the applications
   subsystems and another—by the SE. In secure state, clock gating changes are only enabled indirectly through
   dedicated service requests executed by the SE.
   Ensemble family of devices uses a pin multiplexing scheme, as the number of peripherals with interface
   signals can exceed the number of available pins on the device package. The pin multiplexer enables the
   selection of up to eight different functions per pin. Like the clock gating control implementation, in secure
   state, the pin multiplexing is only possible by dedicated service requests executed by the SE.

2.8 Power Management
   The Ensemble family of fusion processors and microcontrollers features various independent power domains,

   transitions—from power-up to full GO mode, and all modes in between. This scheme achieves optimum

2.9 System Startup and Control

2.9.1 Boot Process
   The SESS performs the role of a system supervisor. After reset, the SESS is the only core that starts execution.
   The SESS initializes the device, sets up the security policies and performs a secure boot for the other
   subsystems. Once the boot is complete, the SE offers runtime services for security, crypto and system
   configuration.
   The boot process starts with the SESS executing boot code stored in its local ROM. Its purpose is to perform a
   basic system initialization and to identify the system context—memory retention states and wakeup events.
   Based on the result, the execution flow proceeds with cold or warm boot scenarios, with or without
   rebooting the related execution domains.
   The cold boot process starts with the SESS configuring the bus infrastructure and Firewalls to enable access
   to the system memory and peripherals. The boot ROM code then accesses the reserved on-chip NVM for a
   cryptographically signed Second Stage bootloader, and after validation, it proceeds with its execution. The
   Second Stage bootloader in the SESS sets up the system clock generator, the PLL operation, and the security

   mechanism. Next, it scans the NVM for valid Application Table of Content (ATOC) and copies memory
   segments to their execution address (RTSS TCMs) if needed, or executes directly from MRAM if directed (XIP
   mode). Finally, the SESS starts each of the subsystem execution domains, bringing them out of reset, and
   then enters a wait loop, expecting application service requests coming from any of the MHUs connected to
   the application cores.
   If the Second Stage bootloader validation fails, or it does not find any application code in NVM, the SESS
   enters a wait loop, expecting a command stream from a dedicated SE UART. This is an abnormal state

2.9.2 Application Deployment in NVM
   Ensemble family of devices features up to 5.5MB of NVM (MRAM) that can store application code and data.
   The layout of the storage space is described in a dedicated memory location called System Table of Content
   (STOC). It contains pointers and attributes to the different blocks of application code and their attributes. The
   STOC is processed by the SE Second Stage bootloader as described in Section 2.9.1 Boot Process.
   The attributes of each binary image specify if it needs to be loaded to an SRAM region. The image loading
   may also be configured to include decryption and/or decompression. Once the SE loads an application image
   to a specific subsystem, it releases its reset signal and starts its operation.

3.1 SESS Introduction
   The Ensemble family of fusion processors and microcontrollers from Alif Semiconductor creates a scalable
   and compatible continuum of highly integrated processors for use in intelligent embedded IoT applications.
   It contains multiple ARM CPU cores for applications processing including Cortex-A32, Cortex-M55 and Ethos-
   U55 cores, along with a security subsystem, on-board memories, and peripherals.
   The SESS is a security subsystem which is responsible for managing and booting the entire device in a secure
   manner. The SESS contains an isolated core and memories and consists of:
     n Arm Cortex M0+ core
     n Crypto Hardware (CC312)
     n One Time Programmable (OTP) memory
     n SRAM
     n ROM
     n SE Peripherals such as UART, Watchdog Timer (WDT), and Real-Time Counter (RTC)

   The SESS initializes the device, sets up the security policies, and performs a secure boot for the other
   subsystems. Once the boot is complete, the SESS offers runtime services for security and system
   configuration.
   The SESS has three software components:
     n SEROM (Initial ROM code that boots the SE)
     n SES (Secure Enclave Supervisor) code image
     n SETOOLS (Alif Security Toolkit—Windows, Linux, or MacOS)

   The SESS Arm Cortex-M0+ core is the first core to execute, which boots from the Secure Enclave Read Only
   Memory (SEROM) and its primary role is to load SES image from the device's internal MRAM-based NVM.
   Once it has completed booting the rest of the Application CPUs, it will then provide Secure Services to the
   other application CPU cores.
   For additional information and details of the tools and processes used to provision security credentials, how
   to use the credentials, how to sign images, how to create the ATOC, and how to run the tools, refer to the
   Alif Security Toolkit User Guide available on the Alif Semiconductor Software & Tools page.
   Details on installing the SETOOLS can be found in the Alif Security Toolkit Quick Start Guide.
   Details on SE services can be found in the SE Host Services API User Guide.

3.2 SEROM Bootloader
   The SEROM code serves as the primary bootloader for the device, running on the Arm Cortex-M0+ core (part
   of the SE) immediately after a Power-on-Reset (POR) or system wakeup. It is the first component in the boot
   chain, with all other cores held in reset until the SESS releases them.
   The main function of the SEROM bootloader is to initialize the device, load and verify the SES code (also
   referred to as SERAM or the second-stage bootloader) from NVM (after POR) or from RAM, and execute it.
   The SES image is signed and must undergo verification before execution.

3.2.1 SEROM Boot Sequence

3.2.1.1 Initialization
   Execution begins in Reset_Handler() function. Then the initialization follows the below order:
     n System power is enabled.
     n The Firewalls are initialized for the SE, so that the M0+ can access all external memories. Address
       translations are configured.
     n UART is initialized with CPU clock speed of 76.8 MHz and a baud rate equal to 115200 baud rate, and the
       banner message is printed.
     n Function main() is called, the CryptoCell (CC312) is initialized, and the Lifecycle State (LCS) state is
       fetched. If this fails, SEROM enters into Recovery mode.
     n Code waits for MRAM to be initialized. If this fails, SEROM enters into Recovery mode.
     n The remaining CC312 initializations are performed. If this fails, SEROM enters into Recovery mode.
     n The code boot sequence is performed by calling BootROM_ColdBootSequence() on the first TOC entry. If
       this fails, code reports error and then calls BootROM_ColdBootSequence() on the second TOC entry. If
       this fails, code reports error and then enters In-System Programming (ISP) based Recovery mode.
   A cold boot sequence occurs if the device is not in Retention mode. In this scenario, SEROM will attempt to
   load code from the NVM (SERAM) memory. If the NVM read fails, the device cannot boot and will enter into
   Recovery mode.

3.2.2 BootROM_ColdBootSequence() Function

3.2.2.1 STOC Localization
   As an example, the MRAM is assumed to be 6MB (0x0060_0000) in size. The last word of MRAM, located at
   offset 0x005F_FFFC, contains the offset of the ATOC within MRAM. The function accesses this word and
   verifies that it is nonzero, less than or equal to the size of MRAM minus ½ megabyte, and a multiple of 16. If
   those conditions are not met, Recovery mode will be invoked.

3.2.2.2 Selected TOC Entry Processing
   The selected TOC entry is at an offset relative to the STOC. For example, the first TOC entry is at offset 0x10
   and the second TOC entry is at offset 0x20. The function validates that this TOC entry offset is valid, that is, it
   is nonzero, divisible by 4, and is within range. If those conditions are not met, it returns an error, thus
   aborting the cold boot sequence.

3.2.2.3 Certificate Chain Location and Identification
   The offset in the selected TOC entry points to the first certificate of a chain. The function determines the
   length of this chain. Valid certificate chains are just a content certificate (length 1), a key certificate followed
   by a content certificate (length 2), or two key certificates followed by a content certificate (length 3). If no
   such sequence exists, return an error, thus aborting the cold boot sequence.

3.2.3 Certificate Chain Processing

3.2.3.1 Raw Loading
   If the certificate chain only contains a content certificate and the LCS is not secure, raw loading is being
   requested. If the LCS state is secure, the function returns an error, thus aborting the cold boot sequence. If
   the content certificate indicates that the code is encrypted, the function returns an error. If the content

Software Reference Manual                                                                          Preliminary Information
                                                          19
ASRM0002 v1.8—December 2024                                                                 Alif Semiconductor Confidential
   certificate indicates that the code is encrypted, it returns an error. If the source address or the target address
   are invalid, the function returns an error. Otherwise, it copies the SES code from the source address (MRAM)
   to the target address (SRAM). Once copied, the function calls the entry point. The primary boot sequence is
   complete.

3.2.3.2 Certificate Chain Verification
   Assume there is either a key certificate followed by a content certificate, or there are two key certificates
   followed by a content certificate. The certificate chain length indicates which of these two options is
   presented.

3.2.3.3 Warm Boot
   The function reads the retention register. If it indicates that SES code is already loaded in SRAM, the function
   accesses the content certificate to determine what address in SRAM is loaded and calls the entry point. The
   primary boot sequence is complete.

3.2.3.4 Cold Boot
   For each certificate in sequence, code calls the cryptocell-boot library function CC_SbCertVerifySingle(). This
   function will compare the hash of the first key certificate’s public key against what is stored in the OTP if we
   are in Device Manufacturer (DM) or secure LCS. It will compare the hash of the second key’s public key
   against the value stored in the first key certificate. It will compare the hash of the content certificate against
   the value stored in the second key certificate. Then, it will decrypt the code if encrypted and copy if from
   MRAM to SRAM as specified by the content certificate. If any error is detected, code returns an error and
   aborts the cold boot sequence. Otherwise, it calls the entry point. The primary boot sequence is complete.

3.2.4 Error and Panic Values
   If an error is returned by any function, it is reported by main(). If an error is so severe that processing cannot
   continue, Recovery mode is called and the code enters an infinite loop awaiting commands from the SE
   UART.

3.5.10 Maintenance and Recovery Mode
   Should the contents of the NVM (MRAM) become corrupted or lost, the initial ROM boot will enter a
   Recovery mode allowing for the recovery of the SESS software in NVM.
   In-System Programming (ISP) is a method by which SEROM can execute operations sent from a Host machine
   to the target. These operations are limited to send the revision data for the device, update MRAM contents,
   and reset.
   These operations are carried out over the Secure Enclave UART (SE UART) using an Alif Semiconductor
   defined protocol. Tools on the Host machine will manage this protocol.
   The ISP protocol is supported by SEROM. It uses ISP primarily as a recovery mode to restore MRAM contents.

   The application CPUs can dispatch service requests to the SESS. This is done using shared memory and the

4 Ensemble Application Anatomy

4.1 Application Architecture
   This section describes application architectures having different memory layouts. Thanks to the multiple
   application processors and many different memory types (NVM, ITCM/DTCM, SRAM), the embedded
   software application can be optimized for performance, size, boot time or ease of debugging. The Ensemble
   processor platform provides a highly flexible bus interconnect that offers different bootloading and execution
   models. The boot process is split between the SE and the application processors. The boot process used
   depends on the security, performance, and memory size limitations. The execution modes differ based on
   the memory location containing the code.
   When the application processor fetches instructions directly from the NVM, the execution mode is referred
   to as eXecute-in-Place (XIP). This mode is traditional for MCUs. Alternatively, the code may be copied from
   the NVM to the TCM memory or SRAM during the boot process, and then executed from there. This mode is
   typical for the TCM-based processors and MPU-based systems. User applications often use a mix of the two
   execution models to combine their benefits—faster boot in XIP mode and better performance when running
   from TCM/SRAM.
   The necessity of different application scenarios stems from the fact that the Ensemble platform is a
   heterogeneous multi-core environment with enhanced security capabilities. The application boot process
   and the individual core reset are controlled by the SESS. The applications, on the other hand, can have
   different security and performance requirements, which affects boot model requirements and how the SE
   will boot these processors. The description of the different boot models references application content
   organized in several segments, each serving specific purposes such as:
     n Code (.text) segment, that is Execute Only (XO) segment
     n Constant (.const) data, Read Only (RO) segment
     n Initialized (.data) data, Read/Write (RW) segment
     n Zero Initialized (ZI) data segment
     n Non-Initialized data segment

   The segments are defined in the linker script (scatter file) with a name, load address, and execute address.
   When the load and the execute addresses are the same, the application can run in XIP mode.


                                                      NOTE

     It is recommended to define at least one such XIP segment for booting. Typically, this is a code
     segment that also contains the vector table definition.


   If both the load and the execute addresses are different, the application startup code invokes a scatter_load
   () function that copies the segments from their load locations to their execute locations. This is typically done
   for the initialized data segment. Certain functions can also be placed in this segment so that they can execute
   faster from SRAM/TCM.
   To define the boot up process, the fusion processor uses the ATOC that specifies which application processor
   or processors to boot, the boot order, and the boot model for each application processor. The ATOC is always
   located at address 0x0 in MRAM and can vary in its length.

   application source code is typically stored in a dedicated folder (Source) under the project root.

   The project folders are as follows:
     n Includes folder: Contains references to the locations where the Common Microcontroller Software
       Interface Standard (CMSIS) header files are stored. These header files are part of the CMSIS drivers and
       the startup code selected during project configuration.
     n Debug folder: It is named after the currently selected project build configuration. It contains the output
       of the compiler (the binary objects) and the output of the linker (the executable or the library being
       build). This folder is created automatically and updated with every build. Selecting Release configuration
       results in folder named Release being added to the project structure and updated with every build
       command.
     n The Run Time Environment (RTE) folder: Contains all CMSIS drivers and device specific source code
       imported from the CMSIS packs. The Device subfolder contains files specific for the CPU core targeted by
       the project. They include the headers with the device specific macro definitions, the vector table
       definition, and the startup code executed once the CPU reset is released.
     n Device folder: Contains a subfolder having the name of the target CPU, which in turn holds all startup
       code, system initialization code, and the scatter file. The latter defines the application memory layout
       that may need to be updated as the application size grows and requires placing of the binary objects in
       different memory regions.
     n Source folder: Contains the application code. In the example above, the LED_blink_baremetal.c contains
       the main() function invoked by the startup code. This folder should be used to store the hierarchy of
       application source code, possibly organized into multiple subfolders.
   The CMSIS project contains one file named after the project, with the extension rteconfig (test2.rteconfig in
   the example above). This file contains the project specific CMSIS configuration. Double-clicking the file name
   opens the CMSIS configuration editor, which enables adding new components or removing the existing ones.
   This process updates the content of the RTE folder described above.

4.6 Linker Script
   The purpose of the linker script is to configure the operation of the linker, placing objects in specific
   segments—code, constants, and initialized data. In the embedded system development, the linker script also
   resolves the external references to address locations, describing the device memory layout.
   The content of the linker script, specifically the load address of the different segments, must be coordinated
   with the SETOOLS configuration file when the boot mode is MCU or Hybrid. In these modes, the NVM
   address where the application image is stored, must match the load address definition in the linker script. In
   case there are several images—their address in the NVM must match each load address in the linker script.

4.7 Applications Table of Contents (ATOC)
   The ATOC is a metafile used by the SE that consists of two parts:
     n   Device configuration file
     n   List of the MRAM application images that execute on the application processors (see Figure 4-9).
   The device configuration file specifies the fusion processor configuration settings that are applied after
   system reset before any application processor starts execution. This includes system clock settings, pins'
   settings, and system allocation (security firewall) settings.
   The list of application images in MRAM provides details on how the SE will process the images using the
   various boot models. For each of the images, there is also a set of descriptors that specifies the type of
   image, image address in the NVM, the boot model, the load/boot address, and other security-related
   options.

6 Application Development Workflow
   The application development workflow is the same as that of any CMSIS-based project development.

6.1 Create Device Configuration File
   By default, an all-access model (all resources available to all cores) is implemented for the Alif Semiconductor
   devices.
   The user can create an intended usage configuration for a device using Alif Conductor tool. Configuration
   options available to the user include CPU cores, memory, peripherals, pins, clocks, DMA, power estimation,
   and miscellaneous configurations.
   Once the user creates the desired configuration, a configuration file can be generated. This file is then fed
   into the Alif Semiconductor Security Toolkit to create a binary image, which is used by the secure boot loader
   to configure the device.

6.1.1 DevKit and AppKit Configuration
   The Ensemble E7 DevKit and AppKit come preprogrammed from the factory with a default all-access
   configuration. This configuration is set up with the kit's pin-outs and allows access to all peripherals by any of
   the application cores (APSS, RTSS-HP, or RTSS-HE). Clocks are programmed to the default frequencies.

6.1.2 Production Device Configuration Using the Conductor Tool
   Use the graphical web-based Conductor tool to configure a chip in 3 major areas:
     n Resources Configuration
     n Pins Configuration
     n Clocks Configuration

   The Alif Conductor tool can be used after proper registration and logging to the Alif Semiconductor site
   https://alifsemi.com/.
   The Help Manual provided with the tool under Main menu icon            guides on how to use each of the tool’s
   configuration tabs.

6.1.2.1 Resources Configuration Management
   An Alif Semiconductor's device consists of multiple cores, multiple memories and almost all possible
   peripherals for embedded world. Not all cores, memories or peripherals are required at the same time for a
   particular project. The Conductor tool offers a way to configure core selection and associate peripherals
   along with that.
   Configuration options supported for any core are:
     n Enabling or disabling the core
     n Setting the boot address for the core
     n Configuring peripheral/memory settings and assigning peripheral/memory to a core


6.1.2.2 Pins Configuration Management
   The General Purpose Input Output (GPIO) pins in Alif Semiconductor's devices are muxtiplexed to support
   multiple functionalities. At any time, device pins can be configured to work in a particular functionality mode.
   Peripherals selected in the Resources tab are automatically assigned to the default pins. If the user tries to
   assign the same pins to different functions, the tool will flag them as errors or warnings.

ASRM0002 v1.8—December 2024                                                               Alif Semiconductor Confidential
6.1.2.3 Clocks Configuration Management
   Cores and peripherals in an Alif Semiconductor's device can work at different (selectable) clocks. Clocks
   configuration settings provide options to select the clock source for peripheral and CPU cores.

6.2 Create or Import Project Files into the IDE
   After defining the device configuration, the next step is to load projects and associated CMSIS-Pack files that
   assist in setting up the initialization of the cores and core subsystems (interrupts, etc.). It is recommended
   that users start from example project files whenever possible.
   After deciding on the device configuration to be used, either the default all-access configuration or a custom
   configuration, the next step is to import any needed project files into the IDE being used.
   It will be necessary to import generic Arm CMSIS-Pack files needed to support the APSS and RTSS cores in the
   device, as well as Alif Semiconductor's specific CMSIS-Pack files with device drivers for all the available
   peripherals in the device.
   Generic Arm packs can be found here:
     n   ARM.CMSIS pack
     n   ARM.CMSIS-Driver pack
   Alif Semiconductor specific packs are:
     n Pack for CMSIS device support: alif_ensemble-cmsis-dfp
     n Pack for Azure RTOS support: alif_ensemble-Azure-RTOS
     n Pack for Free RTOS support: alif_ensemble-FreeRTOS-Components

   These packs are then combined and used to create a project in the IDE. In the respective development
   environment, the user can select the CPU core to be used, create the project, then go into the listing of the
   pack contents, and select the appropriate drivers for the peripherals to be used in the design.
   Application source code can be added to a project by either adding a new file from scratch, or importing
   existing source files. For an initial project, it is recommended that the user imports an existing project and
   uses that as a model for creating further projects.

6.3 Create Debug Configuration
   To have the capability to load and debug a design, it is necessary to create a debug platform definition in the
   tools and then define a specific debug connection. The process of creating a debug platform associates the
   particular debug probe connected to the host system with the board to be used.
   Once a debug platform is created, the user creates a debug connection that associates that particular debug
   probe platform with a specific CPU core and executable file, and specifies what to do after the executable is
   loaded:
     n Connect only
     n Debug from entry point
     n Debug from a specific symbol


6.4 Compile and Build Application
   Once the project has been created with all the required pack libraries and user application code, the next
   step is to compile the code and build the complete application. This process is unique to the particular IDE
   being used. User source code and applications shall use the same compiler for building purposes.



Software Reference Manual                                                                       Preliminary Information
                                                        46

   Any errors noted during the project build need to be taken care of through the inclusion of the necessary
   library or driver elements, or changes to the user application source code.
   Once the project is built with no errors, the user can start debugging the application.

6.5 Debugging a Single Core Application Via Debugger
   Before committing the application NVM storage, each individual design will normally be debugged on the
   target CPU core using a debugger such as ULINKpro. In this case, the system code in the device will perform
   device setup using the default All access configuration, and then the user application code will be loaded into
   SRAM, where the CPU will begin execution.
   The IDE debug tools connect PC's USB port to the target system via a JTAG connector. The debug tools can be
   used to program, debug, and analyze applications, along with Arm DS.
   Once a debug platform has been established and a debug configuration created for the desired CPU core
   (A32, M55-HP, or M55-HE), the debugger can be started and the user can go through the process of looking
   at expected output and setting breakpoints if necessary.
   If changes are needed to the design, the user can stop the debugger, edit the source code, re-build the
   design, and then create a new debug connection, and continue the debugging process.
   This debug process would be used on the designs for each CPU core to be used in the final application until a
   set of functional binary executables is available.

6.6 Using NVM Storage
   The SETOOLS package allows the user to provision the device. This includes programming MRAM with
   application binaries for the Arm Cortex-A32 and Arm Cortex-M55 embedded processors available for user
   applications.
   The tools can interface to the device using a ULINKpro debugger connected to the JTAG port, or optionally
   through a serial port connection to the SE UART, which connects to the SESS (ISP mode). For beta devices (A1
   silicon), only ISP mode is supported.
   These tools operate on binary executables that are boot-from-flash ready and can be programmed into ROM,
   so it will be necessary to convert the output of the design tools you are using into binary form. Use the
   appropriate conversion tool for the particular design environment.

6.6.1 Generate New RoT if Necessary
   The RoT is created with app-gen-rot.py. This operation only needs to be performed once, unless there is a
   need to recreate the RoT with a new set of keys. The release packet contains a sample RoT with
   corresponding keys, and certificates that can be used for experimentation. For actual device provisioning, the
   RoT must be re-generated to create unique keys.

6.6.2 Creating Application Package Binary TOCs
   Edit the build/app-cfg.json file (or a .json file with other name) with images to include in the desired
   AppTocPackage.bin image and copy the binaries into the build/ directory.
   The supplied version of app-cfg.json has a default load addresses for each CPU core. If the user is going to let
   the tools decide where to store the applications in MRAM, it is only needed to specify the binary file name
   for each CPU and set the load and boot flags as desired.
   Run app-toc.py to generate the application package, which will be written out as AppTocPackage.bin to the
   build/ directory.

7.1.1 Message Handling Unit (MHU)

7.1.1.1 MHU Overview
   The MHUs facilitate interrupt-driven communication between two subsystems. Each MHU has two halves
   namely:
     n   A Sender frame or Sender
     n   A Receiver frame or Receiver
   The communication between two subsystems is made possible with one subsystem having the Sender, and
   the other subsystem having the Receiver of a single MHU.
   In Ensemble family of devices, MHUs are implemented in pairs to allow for full-duplex communications, with
   Sender and Receiver being reversed in the MHU pair, that is, each Subsystem A and Subsystem B has Sender
   and the Receiver of a single MHU, where 4-byte data sent by Sender of subsystem A is received by Receiver
   of Subsystem B; similarly, 4-byte data sent by Sender of subsystem B is received by Receiver of Subsystem A.
   By this way full-duplex communication between Subsystem A and Subsystem B is achieved using two MHUs.
   For compliance with the TrustZone technology, each subsystem has two MHUs, Secure MHU (MHU0) and
   Non-secure MHU (MHU1) for secure and non-secure communication, respectively.

7.1.2 Hardware Semaphore (HWSEM)

7.1.2.1 HWSEM Overview
   A need for synchronization while accessing a shared resource (memory or peripheral) by two or more
   independent processing subsystems is fulfilled by the HWSEM. By accessing shared resources with
   synchronization, the possibility of race conditions, deadlock, abnormal behavior among independent
   processing subsystems can be avoided.
   Requests from multiple bus masters to access a shared resource are made atomic and serialized to avoid
   conflicts and race conditions. This is achieved by making processing subsystems wait for the HWSEM
   interrupt to occur before locking/acquiring HWSEM. The locking/acquiring of HWSEM by a specific processing
   subsystem is done by writing its master ID (4 bytes of data) into the HWSEM registers before accessing a
   shared resource. The processing subsystem holding the HWSEM can lock it multiple times, and a
   corresponding counter gets incremented. Any attempt to lock/acquire the same HWSEM by any other bus
   master is refused or blocked until the processing subsystem holding the HWSEM is released. The counter
   value is decremented upon every HWSEM release. If the counter value reaches zero, then HWSEM
   release/free is signaled through an interrupt. The other processing subsystems waiting to acquire the
   HWSEM can handle this interrupt by trying to acquire the HWSEM.
   In Ensemble family of devices, there are up to 16 instances of HWSEM, which are included among the shared
   peripherals. The interrupt requests of these HWSEMs are shared across the multiple processing subsystems.

7.1.2.3 Inter-Process Synchronization with HWSEM
   The primary use case of using HWSEM is to achieve inter-process synchronization while accessing a shared
   resource by a multiple independent processing subsystem. Having synchronization while accessing shared
   resources eliminates race conditions, deadlocks, and abnormal behavior among different subsystems. Each
   subsystem should follow the steps below to achieve inter-process synchronization while accessing shared
   resources:
     1. The processing subsystems wait for the HWSEM interrupt to occur.
     2. Acquire a specific HWSEM before accessing a shared resource, by writing its master ID into BASE_ADDR
        + 0x0 offset.
     3. Check whether the HWSEM acquisition is successful by reading the contents of BASE_ADDR + 0x0 offset
        with the written master ID. If the contents match, then the HWSEM acquisition is successful.
     4. Optionally multiple threads can acquire the same HWSEM by writing master ID into BASE_ADDR + 0x0
        offset. Check the HWSEM count by reading contents at BASE_ADDR + 0x4 offset.
     5. Access the shared resource.
     6. Unlock HWSEM by writing its master ID into BASE_ADDR + 0x4 offset.

7.1.7 Watchdog Timer (WDT_APSS)

7.1.7.1 WDT_APSS Overview
   Most embedded systems need to be self-reliant. It’s not usually possible to wait for someone to reboot them
   if the software hangs or the system crashes. Some embedded designs, such as space probes, are simply not
   accessible to human operators. If their software ever hangs, such systems are permanently disabled. In other
   cases, the speed at which a human operator might reset the system may be too slow to meet the product's
   uptime requirements.
   The WDT is a hardware component that can be used to automatically detect software anomalies and reset
   the processor if any occur. The WDT is based on a counter that counts down from some initial value to zero.
   The embedded software sets the counter’s initial value and periodically restarts it. If the counter ever
   reaches zero before the software restarts it or refreshes the counter, the software is presumed to be
   malfunctioning and the processor’s reset signal is asserted. The processor (and the embedded software it’s
   running) is restarted as if a human operator had cycled the power. Figure 7-6 shows the operation of the
   WDT module.

   The Arm SBSA generic WDT has two-stage timeouts: the first signal (WS0) alerts the system via an interrupt,

7.1.11.2.1 Slave Interface
   The SDMMC supports the AHB slave interface, designed to integrate with the AMBA High-performance Bus

7.1.11.2.2 Master Interfaces
   SDMMC supports configurable master interfaces. Either AHB or AXI can be selected as the protocol for the
   bus master interface.
     n AHB master interface—The AHB master interface is designed to integrate with the AHB bus master
       interface unit that is compliant with the AMBA 2.0 Specification. The AHB master interface is used to
       translate Read/Write transfers initiated by the DMA/CQE (using a generic master interface) into AHB
       compliant transfers on the system bus. The AHB interface transfers the data to and from the system
       memory through AHB master interface.
     n AXI master interface—The AXI master interface is designed to integrate with AMBA AXI bus on the
       application side. The AMBA AXI 3 protocol for the master interface is supported. The AXI master
       interface is used to translate Read/Write transfers initiated by the DMA/CQE (using a generic master
       interface) into AXI 3-compliant bus transfers. The AXI interface transfers the data to and from the
       system memory through the AXI master interface.

   The MRAM (a non-volatile memory) is used to store the APSS images for booting the APSS across multiple
   Power-on-Reset (POR). The stage 3-2 bootloader (bl32.bin) and Linux device tree (devkit-
   <device>.dtb/appkit-<device>.dtb) are stored and executed from the MRAM during the APSS boot up. The
   xipImage and read only rootfs (in cramfs-xip format) can also be stored and executed directly from MRAM for
   use cases that do not require huge code and data spaces.
   The data space required by the Linux kernel and its device drivers is allocated in on-chip SRAM0. The devkit-
   <device>.dtb/appkit-<device>.dtb is loaded from MRAM to SRAM0 before executing xipImage. As the size of
   SRAM0 is limited to 4MB, only Tiny Linux or custom user-space applications, which require less data space,
   can be executed on SRAM0.
   The SRAM1 is used as data space for user-specific graphics and user-space applications.
   The OSPI0 NOR flash memory is used to store custom images, such as xipImage and rootfs (cramfs-xip), that
   do not fit in MRAM. These images can be user-specific, with larger code sizes and greater data space
   requirements.
   The OSPI1 HyperRAM is used as data space for xipImage and user-specific applications that require more
   data space than the available SRAM0 and SRAM1.
   If a use case needs a Linux read/write filesystem, such as ext4, then an SDMMC card can be used to boot
   user-specific Linux distribution.

9.6.1 RTSS SDK Architecture
   The Alif Semiconductor RTSS SDK follows CMSIS-Driver architecture to support its devices across multiple

   For more detailed description of CMSIS-Driver framework, refer to CMSIS-Driver specification.
   As CMSIS-Driver is OS agnostic, it can be used along with different Bare Metal / RTOS environments.

9.6.2 CMSIS-Driver Overview
   The CMSIS-Driver APIs can be divided into two parts: Common Driver functions and Data Transfer functions.
   Common Driver functions include:
     n GetVersion—Provides the version number
     n GetCapabilities—Capabilities supported by the driver
     n Initialize—Allocates the resources and initialize the device
     n SignalEvent—CallBack function for notifying the operation status
     n PowerControl—Controls the device power
     n Uninitialize—De-allocates all the resources and de-initialize the device
     n Control—Configures the device functionalities using control codes (for example, setting parameters,

     n Very flexible task priority assignment
     n Flexible, fast, and lightweight task notification mechanism
     n Queues
     n Binary semaphores
     n Counting semaphores
     n Mutexes
     n Recursive mutexes
     n Software timers
     n Event groups
     n Tick hook functions
     n Idle hook functions
     n Stack overflow checking
     n Trace recording
     n Task run-time statistics gathering
     n Optional commercial licensing and support
     n Full interrupt nesting model (for some architectures)
     n A tick-less capability for extremely low power applications
     n Software managed interrupt stack when appropriate (this can help save RAM)

11.2.2.2 Network Interface Layer
   The Network Interface driver layer provides an interface between the FreeRTOS+TCP networking stack and
   the networking hardware. This layer implements the functions invoked by the stack to initialize and operate
   the Ethernet MAC hardware. This layer is responsible for programming the MAC hardware to send out the
   network packets generated by the networking stack and for routing the incoming Ethernet frames to the
   stack. The FreeRTOS+TCP stack provides different buffer allocation strategies (see Section 11.2.2.3 Network
   Buffer Allocation/Management). If the BufferAllocation_1 strategy is used, the Network Interface driver layer
   is also responsible for statically allocating the memory needed to store network buffers.
   The Alif Semiconductor Network Interface driver supports zero-copy transmission and reception, meaning
   that the network buffers are not copied to local buffers within the driver before being processed by the MAC
   DMA engine. This avoidance of data copy saves CPU cycles and thus increases performance.

11.2.2.3 Network Buffer Allocation/Management
   The network buffers hold the packets that are received and are being sent out by the networking stack. The
   total number of buffers (and their descriptors) is configured by the application using a configuration file (see
   Section 11.2.2.4 Setting Up and Configuring a FreeRTOS+TCP Application) that is used by the stack.
   Additionally, the FreeRTOS+TCP stack provides two buffer allocation mechanisms to choose from. This gives
   the application developer more control over how the buffers are allocated.
   If BufferAllocation_1 strategy is chosen, the memory area for the network buffers is statically allocated by the
   Ethernet Network Interface driver. On the other hand, if BufferAllocation_2 strategy is selected, the network
   buffers are allocated dynamically from the FreeRTOS heap area. Each scheme has its advantages and
   disadvantages. More information on buffer allocation strategies can be found on TCP/IP Stack Network
   Buffers Allocation Schemes.

11.2.5.3 TinyUSB Stack
   TinyUSB stack is responsible for USB Host and Device class implementation, memory resourcing, callbacks,
   stack initialization, initialization of synchronization resources, data transfer routines, buffer management,
   and queue management. The layer interacts with the Application and with the hardware (MCU) through the
   OS Abstraction Layer (OSAL).
   The requests made by USB Host, such as GET_DESCRIPTOR, GET_CONFIGURATION, SET_CONFIGURATION,
   SET_ADDRESS for Device are queued in the TinyUSB stack and made available to the Controller once there is
   an interrupt for device SETUP. The data to USB Host is made available by TinyUSB stack through data transfer
   callbacks and other routines.


Software Reference Manual                                                                        Preliminary Information
                                                             89
ASRM0002 v1.8—December 2024                                                               Alif Semiconductor Confidential
   OS Abstraction Layer: TinyUSB is completely thread-safe by pushing all Interrupt Service Request (ISR) events
   into a central queue, then processing them later in the non-ISR context task function. It also uses
   semaphore/mutex to access shared resources, such as CDC FIFO. Therefore the stack needs to use some of
   the OS's basic APIs. The device SETUP-related requests are queued by OSAL and on-demand, data is passed
   by controller through the respective FIFOs. The OSAL is also responsible for providing basic data structures
   for TinyUSB, which may support concurrency when used with an RTOS. Without an RTOS, it simply handles
   concurrency issues between the main codes and interrupts.
   Dual Role Controller Driver: Driver handles access to hardware registers, endpoint configurations, interrupt
   handling, DMA transfer, and FIFO maintenance. SETUP/Data requests by USB Host to slave device are
   handled by the controller. Depending on the type of interrupt (that is, the type of requests made by USB
   Host) driver makes decisions and interacts with the framework. The return framework calls routines added to
   the OSAL queue and returns data to the Host through DMA transactions. A few of the events handled by the
   controller are XferComplete, XferDataStage, XferInProgress, and XferStatsStage.

11.2.5.5 TinyUSB Working in Device/Host Mode
   In Device mode, stack initialization routines are called from the application, followed by device controller
   initialization routines. The device controller is ready to accept interrupts (Setup from the Host) after


Software Reference Manual                                                                       Preliminary Information
                                                        90
ASRM0002 v1.8—December 2024                                                              Alif Semiconductor Confidential
   configuring the endpoints and device-specific registers. The controller driver gets requests from the Host,
   calls the queued callbacks in OSAL, and returns data to the Host on specific endpoints through DMA. In Host
   mode, Setup packets are created by the Host and sent on Endpoint 0 OUT/IN once the device controller is
   configured and ready to accept Setup packets. The Host continues with additional requests and enumerates
   the device if all information is passed correctly.

12.1 Zephyr Introduction
   Zephyr is a small RTOS for connected, resource-constrained and embedded devices. See more on the
   Zephyr's website.
   Features:
     n A small monolithic kernel
     n Highly configurable / Modular for flexibility
     n Cross architecture support
     n Devicetree support
     n Optimized device driver model
     n A set of protocol stacks such as IPv4 and IPv6, 802.15.4 (LR-WPAN), Bluetooth Low Energy (BLE), CAN-
       FD, MQTT.
     n Virtual File System Interface with LittleFS and FATFS Support

   Zephyr uses a meta-tool called West to execute Kconfig, CMake, and build system commands (Make or
   Ninja). CMake builds applications with the Zephyr kernel in two stages:
     1. Configuration stage: CMakeLists.txt build scripts are executed to generate host-native build scripts.
     2. Build stage: The generated build scripts are executed to compile the application.

12.2 Overview of Zephyr Alif SDK
   The Zephyr Alif SDK (ZAS) is a comprehensive suite of tools that empowers software developers. Designed to
   elevate professionals’ development skills, this software development kit (SDK) enhances proficiency and
   facilitates the creation of high-quality software. With an intuitive design and a wide array of tools, ZAS
   becomes a powerful asset for any software development project. By utilizing this SDK, developers can create
   efficient and top-quality software.

12.3 ZAS Repositories

12.3.1 Zephyr
   The official Zephyr repository serves as the core development hub for the Zephyr real-time operating system
   (RTOS). These components are publicly available and open source, allowing developers from the community
   to contribute and collaborate. The zephyr_alif repository is the Alif Semiconductor port of the public Zephyr
   project repository.
